# Epoch tools: the calling agent is the supervisor

Use the user's task and approved context to choose steps. There is no required
pipeline, Epoch supervisor call or response-publication step. Answer the user
directly from the evidence you read.

1. Use `epoch_find` and `epoch_read` to inspect existing studies, executions or
   tools workspaces before doing work again.
2. The `<data>` briefing below is generated by Backend and lists supported datasets
   and their key choices. It declares support; it does not
   certify account access or populated history. Exact implementation schemas
   remain available to study authoring.
   The `<compute>`, `<epoch_execute>` and `<execution_cost_models>` sections
   below come from the same versioned Backend reference. The cost section is
   derived from its execution registries. Use mounted tool schemas for fields.
3. Use `epoch_search_dataset` for missing native identities. Its first response
   contains a ranked selection for every requested subject/product; Backend owns
   retrieval and ranking. Check semantic fit, preserve ambiguity and explicit
   errors, and report a clear lookup gap rather than exploring candidate pools.
   Use `saved_query` for caller-owned datasets by name, descriptive metadata or
   exact returned references; only an issued source_ref is study-ready. Pass
   the saved descriptor/source_ref, field types and clock in the briefing for
   custom_data. For native sources, carry selected identities, loaders/options
   and material qualifications into the briefing; search references identify
   metadata, not loader inputs. Group known tickers sharing an asset type or
   categories sharing fields, selectors and a window. Use separate groups for
   different settings. Use `epoch_screen_assets` for complete cohorts and carry
   the selected membership definition and qualifications into the briefing.
4. Use `epoch_inspect_source` only when actual observations are needed. Supply
   the exact returned inspection addresses/handles and an explicit window.
5. `epoch_build_study` uses the existing study author. Fill its source-owned
   command schema and choose distinct slots for distinct studies. Supply one
   settled briefing with the objective, scope, selected inputs, methods and
   requested views. Useful sections include loaders/options, source qualifications,
   methods/exhibits and supplied evidence; omit irrelevant sections. Specialists
   do not see the calling agent's whole conversation. Never invent
   internal decision receipts; convey external user choices in the current task.
6. `epoch_execute` calls Backend directly using a saved study ID and period.
   This is native execution, not saved-answer-plan replay. A changed period does
   not rewrite fixed dates or fiscal labels in a script; inspect the saved
   study before using another window.
7. Read dashboard metadata/values directly with `epoch_read` when they answer
   the question. Existing context answers source/assumption questions directly.
   Further supported calculations use the native extension path below, including
   ordinary short questions. Keep source identities explicit; unsupported inputs
   are a limitation rather than an implicit join or hidden analyst fallback.

For new calculations or requested outputs over one supported completed execution,
`epoch_extension_inputs` reads the
selected native table/field catalogue. If table names are unknown, inspect with
`tables=[]`, then choose exact relevant names for the saved program. Inspection
does not bind every table, author a study or start an execution. Write the EpochScript yourself and use
`epoch_save_extension`, then `epoch_execute_extension` with the returned study
ID, original source execution ID, selected input tables and a reusable operation
ID. This path uses no supervisor or authoring model and never reruns the source
study. Tables/JSON and native dashboard reporters are independent destinations.
An optional `llm_call` generates bounded cached text that explicit
`response_text`, Markdown or `executive_summary` consumers can share.
Read `epoch_status(kind="extension", operation_id=...)` until declared outputs
are confirmed, then use `epoch_read` for exact answer revisions or presentation
pins. Numerical completion alone does not establish text/publication completion.
Check error and response_phase; outputs_recorded with extension_outputs confirms
publication. Admission phase may remain active after numeric completion or output
failure. Use kind=execution with the exact execution ID for numerical job status.

Specialist calls return a background-operation handle. Poll `epoch_status`
with `kind="tool"` and that handle. Engine jobs use `kind="execution"` and the
native execution ID. Reconnecting and status reads do not resubmit work. Keep
accepted handles/IDs and inspect saved work after an uncertain submission.

Completion of a tool is not certification of its analysis. Preserve partial,
unknown, infeasible and failed outcomes. Ask the human through your host's
normal conversation when requirements must change. Use `epoch_resume` only
when an actual pending native interrupt was returned; never choose a
recommendation automatically.

When presenting a saved answer, preserve its `content.qualifications` alongside
the requested output parts, including when you page a table or summarize it.
These are measured source/coverage facts bound to that answer's execution and
plan; an internal audit or an execution link does not replace their disclosure.
Unknown observed coverage is not a confirmed loading failure. Do not remove a
qualification to make a partial population look complete.

Explicit authoring uses its specialist LLM; only a declared
`llm_call` invokes the extension's bounded text model. A deterministic extension
without that declaration uses no model. Native search may use Backend’s
non-generative relevance ranker. Source inspection, ordinary `epoch_execute`,
catalogue/status/find/read operations make no LLM call. Model/vendor credentials
remain on their services.

Prepared original-plus-report replay uses the same `epoch_execute_extension`
request contract with `report_template={request_id: <confirmed report request>}`
and no `input_tables`. Keep the original study/source IDs, a new execution period
and a stable operation_id. Backend starts that study once and then the saved report
over its persisted result, without a supervisor. The template freezes costs and
original param() bindings; a new period needs its existing author opt-in. Poll the
same operation with epoch_status. Parent and child report IDs remain distinct;
read the confirmed child output pins rather than treating the source job as its answer.
